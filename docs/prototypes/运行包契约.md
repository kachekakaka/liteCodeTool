# 双平台免安装运行包契约

本契约定义运行包的准备、出包和启动方式。适用 Windows x64 与麒麟 Linux ARM64；领域术语与数据隔离原则见 [CONTEXT.md](../../CONTEXT.md)。

## 开发与运行分开

开发继续使用原有 `npm run dev:demo`、`npm run dev`、`npm test`、`npm run build`，以及开发机 Node（至少 22.16）。发布使用包内独立 Node，不修改系统 PATH，不安装系统服务，也不替换机器已有 Node。

两个目标均固定使用 Node.js 22，同一小版本由 [runtime-resources.mjs](../../tools/runtime-resources.mjs) 的 `nodeVersion` 定义。项目依赖以 `package-lock.json` 为准。运行包仅含 Node 可执行文件及完整许可证，不携带 npm、VS Code 或开发用 `node_modules`。

## 准备和出包

在已经安装项目开发依赖的 Windows 或 Linux 准备机执行：

```text
npm run prepare:runtime
npm run package:release
```

- `prepare:runtime` 访问 Node 官方固定版本地址，下载 Windows x64 可执行文件与 Linux ARM64 压缩包，并按官方 SHA256 清单校验。只解出所需运行文件和许可证；已下载且摘要一致的文件可复用。
- 下载缓存位于 `../liteCodeTool_tmp/runtime-downloads/`，经过准备的资源位于 `../liteCodeTool_tmp/runtime-resources/`。资源可以整体复制到内网准备机，保持相同的相对目录结构。
- `package:release` 不访问网络。它校验本地运行资源、重新执行标准构建，再分别装配目标包。资源缺失时明确报错，不静默下载或使用系统 Node 代替目标运行时。
- 缺少源码开发依赖时须事先在外网执行 `npm ci`；内网开发机可使用既有 Windows x64 离线开发包。新增打包依赖后需按现有流程重新准备离线开发包。
- 两个目标均输出 `.tar.gz`、对应 `.sha256`，以及便于本机验证的未压缩目录，位于 `../liteCodeTool_tmp/packages/`。文件名包含应用版本和目标平台，如 `liteCodeTool-<版本>-win32-x64.tar.gz`。
- 每包附带 `manifest.json`，记录目标平台、固定 Node 版本、资源来源与摘要、应用构建信息。压缩包中的 Linux 启动脚本和 Node 显式设置可执行位，可在 Windows 准备机生成。
- 更新固定 Node 版本后，重新准备资源并出包，不覆盖系统 Node。

## 包内结构

```text
liteCodeTool-<版本>-<平台>/
  start.cmd 或 start.sh
  iframe-test.cmd 或 iframe-test.sh
  iframe-test.mjs           # 跨来源 iframe 测试宿主
  iframe-flight.litecode.json # 内置模板生成的飞行高度测试配置，可导入为独立大屏
  launcher.mjs
  runtime/                 # 对应平台 Node 和 LICENSE
  app/                     # 已编译的页面、服务端与共享核心
  licenses/
  THIRD_PARTY_NOTICES.md
  manifest.json
  README.txt
```

完整解压归档。Windows 可使用支持 tar.gz 的解压工具，或系统提供的 `tar -xzf <压缩包路径>`。Linux 使用 `tar -xzf <压缩包路径>`，应保留归档权限。

| 平台 | 演示模式 | 真实模式 |
| --- | --- | --- |
| Windows x64 | 双击 `start.cmd` | `start.cmd --live` |
| 麒麟 Linux ARM64 | `sh ./start.sh` | `sh ./start.sh --live` |

附加 `--no-open` 可禁止自动打开浏览器，适用于无桌面服务器。脚本可以从其他工作目录调用，路径包含空格时仍正常。进程前台运行，按 Ctrl+C 退出。

默认数据目录为运行包文件夹同级的 `liteCodeTool_datas`，使用 `DATA_DIR` 可指定既有数据目录；演示与真实模式沿用原来的数据区分。升级时替换应用包，不删除外部数据目录。旧版手动运行 `launcher.mjs` 曾在启动器所在目录内创建数据；升级时可用 `DATA_DIR` 显式指向原目录，不自动移动既有数据。

在 `liteCodeTool_tmp` 内试运行未压缩目录或解压包时，须用 `DATA_DIR` 指向外部数据目录的独立验证子目录；现有服务禁止把运行时持久化数据写入临时目录。验证日志和报告仍放在外部临时目录，验证完成后清理本次创建的数据子目录。

`PORT`、真实数据接入凭据以及监听行为沿用当前服务。当前开发与发布默认监听所有 IPv4 网卡，支持局域网访问；这不代表此前方案中其余组件工坊交互改动已经实施。大屏管理与嵌入使用方法见[快速入门手册](../../快速入门手册.md#集成到其他系统)。

包内 `README.txt` 提供无需开发工具的跨电脑测试步骤。`iframe-test` 启动脚本调用包内 Node，支持 `--base`、`--a`、`--b`、`--port`，分别指定大屏服务地址、两份大屏 ID 和独立宿主端口。从另一台电脑测试时，服务地址须使用可达的局域网 IP。测试配置由内置模板生成，包中不得包含用户的运行时配置或数据。`manifest.json` 记录源码提交及出包时是否存在未提交改动。

## 平台验证边界

Linux ARM64 的 Node 官方二进制要求内核至少 4.18、glibc 至少 2.28，实际麒麟版本需满足这些条件；不是所有标为“麒麟”的安装版本都自动视为兼容。[Node.js 22 官方平台要求](https://github.com/nodejs/node/blob/v22.x/BUILDING.md#platform-list)

最低验证：

1. 运行现有核心测试和标准构建。
2. 两种平台的运行资源通过摘要与二进制架构检查，确认 Linux 归档可执行位正确。
3. 在 Windows 实际解压后使用包内 Node 启动，检查主页、深层路由、API 和退出后端口释放；演示与真实模式分别验证，运行时数据放外部数据目录的独立验证子目录。
4. 在目标麒麟 ARM64 设备运行 `uname -m`、`uname -r`、`ldd --version`，记录实际环境，再用包内 Node 启动并验证页面、保存和 WebSocket。

跨平台装配成功只说明包内容正确，不代表目标平台实际运行已通过。云端 Linux x64 环境可以做代码检查、构建和装配校验，不能直接执行 ARM64 二进制，也不能替代 Windows 或麒麟实机结论。
